# Document State Tracking System Integration Plan

**Date:** 2026-05-26
**Status:** Approved

## Part 1: Problem Understanding

The agentic harnesses generated by `harness-wf` currently lack an explicit, queryable state machine for documents (designs, plans, specs). Because there is no central registry (`manifest.json`) or structured progress tracking:
1. **Hooks** cannot deterministically matrix-match or route tasks based on document state.
2. **Planner agents** lack a unified view of what designs exist or are proposed.
3. **Implementer agents** lose context between sessions because there is no parallel tracking of completed vs. remaining work for a specific design.

The goal is to complete the integration of the template-based Document State Tracking System (manifest registry + strict folder organization + progress docs) into the `harness-wf` boilerplate so that every newly minted harness gets this deterministic state management, and agents actively update it.

## Part 2: Technical Plan

The boilerplate directories and hook scripts are already present in the codebase. The remaining technical plan focuses on integration and enforcement. The architecture relies on a hybrid feedback loop:
1. **The System Prompts (The "Software"):** The agents (Planner, Implementer, Verifier) are instructed in their prompts to update the manifest and create progress docs.
2. **The Pre-Commit Hook (The "Hardware Enforcement"):** `doc-manifest-validator.sh` runs automatically every time an agent tries to commit code. It reads the manifest and the file system.
3. **The Guarantee:** If an agent hallucinates, skips a step, or forgets to update the manifest, the pre-commit hook **fails the commit**. It spits out a rigid `stderr` message. This error goes directly back into the agent's context window. The agent reads the error, corrects the missing file or manifest state, and attempts the commit again. 

## Part 3: Alternatives Considered

1. **Relying solely on folders/filename prefixes (e.g., `proposed_feature.md`):** Ruled out because renaming files constantly breaks references, and it is harder for hooks to quickly query the overall state of the project without scanning the whole filesystem.
2. **Using a Database or YAML for the registry:** Ruled out because JSON is native to most scripting tools (like `jq`), highly git-friendly, and simple for agents to read and write without extra libraries.
3. **No Central Registry (Hooks scan the filesystem):** Ruled out because it lacks a single source of truth. Relying on filesystem parsing makes the hook logic complex and brittle.
4. **Automatic State Transitions (e.g., tests pass = auto-move to completed):** Ruled out because passing tests do not necessarily mean business requirements are met. We need the agents' semantic intelligence to make that judgment, backed by the hooks for enforcement.

## Part 4: Detailed Implementation

The core directories and hook files are already stubbed in `src/harness/templates/boilerplate/`. This implementation focuses on integrating them into the agent prompts and the Python routing logic.

1. **`src/harness/templates/boilerplate/agents/planner.md`**:
   - **Rationale:** The Planner still relies on older instructions and needs to integrate with the new manifest.
   - **Change:** Inject instructions to check `docs/manifest.json` before designing. Instruct it to append new designs to the manifest with `state=proposed` when finished, instead of just saving to `artifacts/`.

2. **`src/harness/templates/boilerplate/agents/implementer.md`**:
   - **Rationale:** The Implementer needs to drive the state machine forward.
   - **Change:** Inject instructions to move the target design from `proposed` to `inprogress` in the manifest upon starting, and to create/maintain the `docs/inprogress/{design_name}-progress.md` file.

3. **`src/harness/templates/boilerplate/agents/verifier.md` (and reviewer.md)**:
   - **Rationale:** The Verifier needs to gate the completion of a design.
   - **Change:** Inject instructions to validate the progress doc against the design spec and move the state to `completed` in the manifest on PASS. Archive the progress doc to `docs/reference/`.

4. **`src/harness/hooks/prompt_classifier.py` & `src/harness/runtime/dispatcher.py`**:
   - **Rationale:** The Python routing engine needs to use the new manifest instead of blindly checking for artifact files.
   - **Change:** Refactor the dispatcher/classifier to execute `bash ./hooks/doc-state-router.sh json` (which is registered in `hooks.json`). Use the returned JSON state mapping (what is proposed, what is inprogress) to deterministically route the user's prompt (e.g., if there is an `inprogress` doc, route to Implementer; if there are only `proposed` docs, route to Planner or ask the user).
